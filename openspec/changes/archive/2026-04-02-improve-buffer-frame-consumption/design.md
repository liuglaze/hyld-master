## Context

当前链路中，客户端使用 `sync_frameID + ceil(RTT/2) + inputBuffer + jitterBuffer` 估算 `targetFrame`，然后把本次输入上报为 `OperationID=nextFrame`。服务端虽然已经把 `OperationID` 解释为客户端声明的目标帧，但在消费阶段仍以 `lastConsumedMoveFrame + 1` 为优先目标；若该帧缺失，则会直接接受窗口内更大的合法帧。这导致“客户端投递到未来帧”和“服务端按当前帧严格消费”之间存在语义断裂。

这次改动跨越客户端动态追帧、服务端移动输入缓冲与联调观测日志，属于跨模块时序语义调整，且会影响输入手感、网络抖动容忍与缺帧表现，因此需要单独设计文档明确端到端决策。

## Goals / Non-Goals

**Goals:**
- 让客户端 `targetFrame` 估算更接近输入闭环传播延迟，改为基于完整 RTT、抖动余量和安全余量。
- 让 `OperationID` 在端到端链路中稳定表示“该次输入要命中的目标权威帧”。
- 让服务端在每个权威帧只消费 `SyncFrameId == 当前 frameid` 的移动输入，不再跳吃未来帧。
- 在当前帧目标输入缺失时，继续用上一条有效移动做短时兜底，以保持战斗循环连续。
- 保留对未来帧输入的缓存能力，使未来输入等待其对应帧到达后再消费。

**Non-Goals:**
- 不修改攻击输入的独立缓存与去重语义。
- 不引入新的网络协议字段，继续复用现有 `OperationID` / `ClientAckedFrame`。
- 不在本次改动中重做客户端预测/和解架构。
- 不承诺消除所有高丢包下的输入迟滞；本次优先解决时序一致性问题。

## Decisions

### 1. 客户端目标帧改为完整 RTT 口径
客户端将 `targetFrame` 从“权威帧 + 半 RTT + buffer”改为“权威帧 + 完整 RTT + 抖动余量 + 安全余量”。理由是：客户端看到的 `sync_frameID` 已经滞后于服务端半个 RTT，而当前输入再次返回服务端还要再经历半个 RTT，因此输入真正稳定落到服务端消费点更接近一个完整 RTT。

备选方案：
- 保持 `RTT/2`：实现简单，但继续低估闭环时延，容易让目标帧偏前。
- 仅增加旧 `inputBufferSize`：能缓解一部分抖动，但语义混杂，不如直接把完整 RTT 和安全余量拆开表达。

### 2. 服务端消费基准改为当前 `frameid`
服务端每个 tick 仅查找 `SyncFrameId == frameid` 的移动输入；找到就消费，找不到则不推进消费进度并进入兜底移动。这样客户端声明的目标帧与服务端实际消费帧完全对齐，避免“客户端说投递到 120，服务端却在 118/119 先吃掉 121”这种语义撕裂。

备选方案：
- 继续以 `lastConsumedMoveFrame + 1` 为基准：可以维持按序概念，但会引入第二套输入消费时钟，与服务端权威帧时钟脱节。
- 缺帧时接受最小更大合法帧：对乱序更宽容，但会压缩输入节奏并打乱客户端的目标帧声明。

### 3. 缺帧时仅沿用上一条有效移动，不提前消费未来帧
如果当前 `frameid` 对应输入未到，服务端继续广播当前帧，但移动部分沿用 `lastValidMove`。未来帧输入继续保留在缓冲区中，等待对应帧到来时再消费。该策略保留现有惯性兜底的平滑感，同时消除未来帧抢跑。

备选方案：
- 缺帧立刻停住：时序最严格，但抖动下角色容易明显顿停。
- 连续缺帧后归零：可能是后续调优项，但本次先保持现有短时惯性模型，减少行为面变化。

### 4. 入缓冲仍允许未来帧存在，但过旧输入继续拒绝
服务端接收阶段继续按 `SyncFrameId` 维持升序窗口，并拒绝 `SyncFrameId <= 当前 frameid` 或已被实际消费的陈旧输入。这样既保留预投递未来帧能力，又保证严格消费模型下不会回吃旧帧。

备选方案：
- 仅允许写入 `frameid` 附近很窄的窗口：会增大客户端轻微超前时的丢输入风险。
- 不再维护有序列表：会增加消费阶段查找复杂度和歧义。

### 5. 日志从“按序/跳吃”切换为“当前帧命中/缺帧兜底/未来保留”
验证日志应反映新的模型：
- 当前帧命中并消费
- 当前帧缺失，沿用上一有效移动
- 接收阶段拒绝陈旧输入
- 缓冲已满淘汰最旧未来输入
这样联调时可以直接验证“没有 future frame 抢跑消费”。

## Risks / Trade-offs

- [输入体感变钝] → 完整 RTT 目标帧会让输入更保守；通过限制 safety/jitter 余量并在联调中调参缓解。
- [高丢包下移动更依赖兜底惯性] → 保留短时 `lastValidMove`，避免角色瞬时停住；若后续出现粘滞过强，再单独增加“连续缺帧后归零”策略。
- [未来输入长期堆积导致缓冲淘汰频繁] → 继续维持缓冲容量上限与淘汰日志，联调时观察 targetFrame 是否过远。
- [旧规格和文档与实现不一致] → 同步更新 OpenSpec、CLAUDE 文档和 BothSide 说明，明确新语义。
- [客户端/服务端公式不一致导致偏差] → 在联调日志中同时输出 `syncFrame`、`targetFrame`、`uploadOperationId`、服务端 `frameid` 与消费结果。
